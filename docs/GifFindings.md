# GIF 实现与性能记录

> 本文件合并「算法分析」「量化器优化建议的实测复核」「GIF 性能实验」三份旧文档。
> 结论：编码瓶颈是**抖动/量化的串行依赖链**，解码瓶颈是 **LZW 位流解包 + 前缀指针追逐**，
> 两处都不可指令级向量化；已落地的收益来自 LZW 编码哈希修复与直方图并行门控。

## 0. 架构与文件职责

```
编码 Encode:  RGB/RGBA → Quantizer(量化+LUT+抖动) → 头/调色板 → LzwEncoder → 容器
解码 Decode:  容器解析 → LzwDecoder(索引) → RenderFrame(调色板展开) → RGB/RGBA
```

| 文件 | 职责 |
|---|---|
| `GifFormat.cs` | 格式探测（"GIF" 头，可复位流位置） |
| `GifAdapter.cs` | 对外适配器；量化器选择（默认 `OctreeBayer`，可切 `WuFloydSteinberg`） |
| `GifEncoder.cs` | 单帧 / 透明 / 动画（RGB / RGBA） |
| `GifDecoder.cs` | 头/扩展解析、LZW 调用、调色板展开、disposal、interlace |
| `OctreeQuantizer.cs` | **默认**量化器：八叉树 + Bayer 抖动 + 15 位 LUT |
| `Quantizer.cs` | 可选量化器：Wu 5-bit 直方图 + Floyd–Steinberg 抖动 |
| `LzwEncoder.cs` / `LzwDecoder.cs` | LZW 编码（Fibonacci 哈希字典） / 解码（位流 + 像素栈 + `pshufb` 反序） |
| `GifTiming.cs` | 分阶段耗时统计，默认关闭、热路径零开销 |

**已纠正的过时说法**：早期文档把 `Quantizer.cs` 的 Wu 实现当成唯一/默认量化器。
实际默认是 `OctreeQuantizer`（`GifAdapter.QuantizerKind = OctreeBayer`，Bayer 幅度默认 8），
Wu+Floyd–Steinberg 保留为可选项。**下文 §4 的热点数据是在 Wu 路径为默认时测的**，
引用时必须带上这个前提。

## 1. 量化器

### 1.1 Octree + Bayer（默认）

- 15 位下标（R/G/B 各 5 bit）查 32768 项 `_mapLut`；不抖动路径的向量版一次处理 16 像素（48 字节），
  解交织出 R/G/B 三平面，`psrlw 3` 得 5-bit 分量后**仍用标量查表**——字节表 + 15 位下标在 AVX2 下
  没有可用向量指令（NEON 的 `TBL` 最多 4 张表 = 64 字节，同样无解；SVE 在 M4 上不可用）。
- 抖动用 `offTab[y & 3]` 的 4 KB Bayer 表，SIMD 加载覆盖，不构成瓶颈。
- 解交织走 `SimdCompat.LoadRgb24Unzip3`：arm64 `tbl` / x86 `pshufb`。
  曾评估的 ARM `LD3` 单指令方案实测**慢 9.4%**，已否决（见 ArmFindings.md §8.2）。

### 1.2 Wu + Floyd–Steinberg（可选）

| 子阶段 | 算法 | 复杂度 |
|---|---|---|
| `BuildHistogram` | 每像素 `(r>>3, g>>3, b>>3)+1` 落到 5-bit 网格（33³ = 35937 bin），累加 5 个矩 | O(像素) |
| `CalculateMoments` | 3D 前缀和（integral volume），任意 box 的矩查询降到 O(1) | O(35937) |
| `Split` / `Variance` | 沿三轴按一阶矩平方和贪心切分，最多 255 次切出 ≤256 box | O(255×3×31) |
| `BuildMappingLut` | 35937 个 5-bit 网格点各自映射到最近调色板索引，并行构建 | O(35937×256) |
| `ApplyDitheringWithLut` | 误差扩散 7/16、3/16、5/16、1/16，已改写为**滚动寄存器**形式 | O(像素) |

评价：Wu 的 5-bit 直方图 + 矩前缀和 + 一阶矩代理选切点是标准最优实现；抖动滚动寄存器化
把每像素 12 次内存读写降级为寄存器，且**结果逐字节一致**——这是本项目最值得肯定的优化之一。
但它同时是全编码的绝对热点（见 §4）。

## 2. 编码侧其余部分

- **LZW 字典查找**：64 位乘法散列（`0x9E3779B97F4A7C15`）+ 32768 槽位（装载因子 0.12）+ 线性探测；
  槽位 64 位打包 `((fcode+1) << 12) | code`，键与值同处一条 cache line。256 KB 超 LOH 阈值故走 `ArrayPool`。
  **原实现的哈希是真实算法缺陷**：`h = (c << 4) ^ ent` 中 `c ≤ 255`、`ent < 4096` ⇒ `h` 恒落 `[0,4095]`，
  8191 槽位只用一半、装载因子 1.0、探测链严重退化。修复后编码 lzw **28.998 → 21.189 ms（1.37x）**。
  **踩过的坑**：32 位放不下（20 位键 + 12 位值 + 1 位占用 = 33 位）；用 `uint` 并把空槽记为 0 时，
  `fcode == 0`（即 `c=0, ent=0`）会被误判命中、md5 对不上，必须用 `ulong` 存 `fcode + 1`。
- **容器**：单帧 GIF89a + GCT + LZW + Trailer；色深取最小满足调色板位宽，min code size 取 `max(2, depth+1)`。
  透明 RGBA **预留索引 0**（不透明索引整体 +1），代价是多占一槽、调色板满 255 时色深顶高 1 位。
  动画逐帧独立量化 + 每帧局部色表（LCT），disposal=0（RGB）/ 2 + transIndex=0（RGBA）。

## 3. 解码侧

- **容器解析**：按块遍历 Header/LSD → GCT → 扩展（GCE 透明度+disposal+delay、NETSCAPE2.0 循环）→
  Image Descriptor；`ReadExact` 保证整块读全，可 seek 时直接跳过无关扩展。
  `delayCs*10 < 10 ? 10 : delayCs*10` 把 0 延迟兜底为 10 ms（多数查看器约定）。
- **LZW 解码**：位缓冲按需从子块补充、`clear/end` 码、首码特例、未定义码输出 `oldCode` 首字符、
  前缀链展开进 `pixelStack`。`ReverseCopy` 对长度 ≥16 的串用 SSSE3 `pshufb` 整块反转。
- **调色板展开**分三条路径：
  1. **整画布不透明**（`opaqueFullCover`）→ `RenderFullCanvasOpaque`：地址连续、无边界判断，
     AVX2 `vgatherdps` 一次取 8 个调色板色、RGBA 直接 32 字节写，RGB24 用 `pshufb` 把 4 像素压成 12 字节；
  2. 逐行普通：散写 + `dx<w`/`dy<h`/`idx<trans` 判断；
  3. interlace：4-pass 逐像素散写。
  `opaqueFullCover` 靠 `AllIndicesInRange`（Vector 水平 max 归约）确认索引全在调色板内，否则会漏写像素。
- **背景/disposal**：`FillBackground` 构造 16 像素模式块后指数式自我拷贝扩散（memcpy 级）；
  背景色**延迟到首帧解出索引后**再决定是否填充——首帧整幅覆盖且无透明时整画布填充是死写，直接跳过；
  disposal 3 的 `backBuffer` 仅在真的遇到时才分配。

## 4. 性能热点（Wu 路径为默认时的实测，2400×1800）

| 方向 | total | 分阶段 |
|---|---|---|
| 编码 | 78.2 ms | **quantize 59.5 ms（76%）**、lzw 18.5 ms |
| 解码 | 14.2 ms | render 2.1 ms、**lzw 12.0 ms（85%）** |

**量化内部**：`ApplyDitheringWithLut` 约 54 ms（**占 quantize 90.8%**），直方图 3.2 ms（5.4%）、
`BuildMappingLut` 1.1 ms（1.8%）、`CalculateMoments` 0.17 ms、`Split` 0.28 ms。
交叉验证：`--dithering off` 时 quantize 只有 6.375 ms。

**抖动为什么不可向量化**：Floyd–Steinberg 是逐像素非线性递推
`carry = (clamp(pixel + rowIn + carry) - palette[lut[...]]) * 7/16`，clamp 使递推非仿射，无法前缀化；
R/G/B 三条链本来就并行，塞进一条 `Vector128` 只是把 3 次标量运算换成 1 次，**缩短不了链长**。

两项实验（同二进制，产物 md5 一致）：

| 实验 | 结果 |
|---|---|
| 去边界检查（指针 + `Unsafe`，每像素少 ~26 uop） | quantize 60.22 → 61.70 ms，**反而慢 2%** ⇒ 不是吞吐受限 |
| 依赖链探针（把 LUT 与调色板两次依赖加载换成常数） | quantize 60.8 → 23.3 ms ⇒ 其中约 **35 ms 是贯穿两次依赖加载的串行 L1/L2 延迟** |

⇒ 封死性上界：即便把直方图/矩/切分/LUT **全部做到零耗时**，quantize 59.5 → 54.8 ms，
**端到端编码最多快 6.1%**，而真正可向量化的只有 1.1 ms 的 `BuildMappingLut`。**量化侧 SIMD 无意义**，
方向应是缩短依赖链（LUT 落 L1、换更小的两级表降 L2 命中率）。

**解码 LZW**：输出阶段只占 ~10%（其中一半已被 `pshufb` 拿走），其余 90% 是变长位域串行解包 +
`code = prefix[code]` 指针追逐（488 万次依赖加载）。把 SIMD 反序下探到 len ≥ 5 实测**更慢**。
详见 [PerfReport.md](PerfReport.md) §4.1。

## 5. 优化建议的实测复核

早期一份 19 节的量化器优化建议，逐条对照源码实测后**只有一条带来了保留的改动**
（其余或收益≈0、或改变产物字节、或根本不是热点）：

| 建议 | 是否属实 | 处置 |
|---|---|---|
| 小图禁用直方图多线程 | **属实，且收益被低估** | ✅ 已实施 |
| `m2` double → long | 属实（整数精确、产物一致），但**收益≈0** | ❌ 回退 |
| LUT 用整数距离 | 属实（逐位一致），但**收益≈0** | ❌ 回退 |
| 并行 merge 替代 lock merge | 开销属实，但直方图只占编码 4.5% | ❌ 不做 |
| 抖动改定点整数 | 可行，但**改变产物字节** | ❌ 不做 |
| `Split` / `CalculateMoments` 不是热点 | 属实 | 不动 |
| 抖动滚动寄存器已优化，别动 | 属实 | 不动 |
| 先 benchmark 再上 `Vector256` | 属实 | — |

**直方图门控（唯一落地项）**：同二进制 A/B（`SIC_Q_HIST_FORCE_PAR`），每组 5 次中位数：

| 尺寸 | 抖动开 | 抖动关 |
|---|---:|---:|
| 512×512 | **−40.1%** | **−50.4%** |
| 800×600 | −26.7% | −43.7% |
| 1024×1024 | −10.6% | −16.8% |
| 1600×1200 及以上 | ≈0（走并行） | ≈0 |

8 尺寸 × 抖动开/关共 16 组产物**逐字节一致**。

两处对原建议的修正（第三条是理由纠错）：

- **固定阈值 100K 像素是错的**。并行固定开销随线程数增长，交叉点实测 4 核 ≈ 0.5 MP、8 核 ≈ 1.05 MP、
  24 核 ≈ 1.6 MP；按 100K 硬编码会白丢 0.1–1.6 MP 区间的 10%–40% 收益。
  实现改为 `60_000 × ProcessorCount + 300_000`，4/8/16/24 核（`DOTNET_PROCESSOR_COUNT` 模拟）验证差距在噪声内。
- **优先级排错了**。原建议把 `m2` 排第一、直方图排第三；实测恰好相反——直方图门控贡献几乎全部收益。
- 「`double`→`long` 减少缓存占用」的理由也是错的：两者都是 8 字节，缓存占用一点没变；
  真正省下的只有每像素 3 次 `int→double` 转换，而这个循环是散射写带宽受限。

## 6. 已否决（勿重复尝试）

| 方向 | 实测 | 原因 |
|---|---|---|
| 量化侧 SIMD（直方图/矩/LUT/抖动） | 端到端上界 6.1% | 抖动 90.8% 的耗时在串行依赖链 |
| 抖动去边界检查 | 反而慢 2% | 延迟受限，非吞吐受限 |
| LZW 解码「直写输出」（`strLen` 表） | lzw 1.07x，性能提升不理想 | 输出阶段仅占 10% |
| 位缓冲一次补 4 字节 / `prefix`+`suffix` 打包单 int / 二级跳转表展开两像素 | −4% ~ −12% | 分支与地址计算抵消收益 |
| SIMD 反序下探到 len ≥ 5 | +0.5 ms | 每串多一次掩码表加载 + 守卫分支 |
| 定点抖动 | — | 改变产物字节，违反验收口径 |

## 7. 仍可改进（都非热点）

| 方向 | 现状 | 备注 |
|---|---|---|
| 动画复用 `Quantizer` 实例 | 每帧 `new Quantizer()` 都要租借/清零 5×35937 longs（~1.44 MB）+ `double[35937]` | 改动小、风险低；仅 Wu 路径 |
| 动画跨帧优化 | 逐帧独立量化 + 独立 LCT，无帧差/调色板复用 | 体积收益明显，但需处理 disposal 语义 |
| 透明 RGBA 的索引 0 预留 | 强制占一槽、可能顶高色深 1 位 | 边缘体积 |
| interlace 路径 SIMD | 纯标量 | 罕见，性价比不高 |
| 降低 5-bit 直方图到 4-bit | — | 画质可能有可见差异，不建议默认 |

## 8. 一句话结论

算法选型正确、优化方向经过严格实测验证。编码瓶颈稳定在「抖动/量化的串行依赖链」，
解码瓶颈在「LZW 位流解包 + 前缀指针追逐」，**两处均为指令级不可向量化的串行结构**；
后续若要突破，应转向算法层（缩短依赖链、跨帧复用），而不是继续投 SIMD。
