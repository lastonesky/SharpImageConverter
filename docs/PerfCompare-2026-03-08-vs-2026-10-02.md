# SharpImageConverter 半年性能对比报告

- 基线: `baseline (23ab67b, 2026-03-08)`
- 当前: `current (HEAD, 2026-10-02)`
- 生成时间: 2026-10-02 18:58:02
- 机器: Intel(R) Core(TM) Ultra 7 270K Plus, 63 GB RAM
- 运行时: 10.0.401 SDK / .NET 10.0.12, 工作站 GC(非并发), Release
- 口径: 内存输入, 预热 1 轮 + 正式 N 轮(按像素量自适应 2~12 轮), 每轮前强制 full blocking GC
- 聚合: 每个版本独立跑 3 轮; 先对每轮内的 N 次取中位数, 再对 3 轮的中位数取中位数
- 一致性: 每轮校验输出字节数与采样哈希, 任一不一致会标记 [UNSTABLE](本次 0 项)

> 约定: **SpeedUp = 基线耗时 / 当前耗时**, 大于 1 表示当前版本更快; Delta% 为提速百分比。
> **轮间波动**列 >=30% 的项受环境/线程池抖动影响较大, 数值仅供参考。

### 方法与已知事项

1. 语料由**当前版本**生成一次, 两个版本读的是同一批文件/同一份 raw 像素, 保证输入字节完全一致。
2. 大图档使用 ``examples/progressive.jpg``(10650x13426 = 143 MP, 渐进式 JPEG), 覆盖解码/灰度/缩放/编码。
3. **WebP 143 MP 编码的特殊说明**: 首轮测出 0.25x 的"回退"后做了交叉验证 —— 把两版解码出的 143 MP 像素分别落盘,
   再用**同一个**二进制分别编码两份像素, 结果是: 两版编码"HEAD 解码像素"都约 32 s, 编码"基线解码像素"都约 8 s,
   与用哪个版本编译无关(两版像素平均差仅 0.051/255, 仅 3.75% 字节不同, 最大差 16)。
   即 libwebp 对该图有极强的**内容敏感性**, 该差异来自解码输出的 ±1 级差异, 不是 WebP 编码路径的性能回退
   (``WebpCodec.cs`` 半年只改了 4 行且都在解码路径, 两个版本打包的 libwebp.dll 也完全相同)。
   为消除这一干扰, 大图档的非解码项统一改用固定的 raw 像素作为输入。
4. GIF 编码默认量化器从 Wu+Floyd-Steinberg 换成了 Octree+Bayer, 输出体积会变化(见文末表格), 属于算法变更而非性能问题。
5. 基线版本的 JPEG 编码存在明显的双峰抖动(例如 77 KP 的 q90 编码在 1.2 ms 与 30 ms 之间跳变), 这是基线自身的线程池行为, 已通过 3 轮取中位数抑制。
