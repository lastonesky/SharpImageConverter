# 性能实测记录与已否决方向

> 本文件是**性能类改动的唯一记录**：哪些方向做过、实测多少、哪些已被证伪（勿重复尝试）。
> 画质/体积类结论见 [Optimize.md](Optimize.md)，ARM 移植见 [ArmFindings.md](ArmFindings.md)，
> GIF 专项见 [GifFindings.md](GifFindings.md)，SIMD 实现陷阱见 [SimdPitfalls.md](SimdPitfalls.md)。

## 1. 验收口径与测量方法

- **看指标本身有没有变好，不看百分比**。性能准入门槛已于 2026-10-10 整体废止：
  项目不再设「提升不足某个比例即视为无效」的门槛，也不再以提速立项
  （见 `CHANGELOG.md` → 1.1.0 → 规则）。因性能原因不保留的改动，统一表述为「性能提升不理想」。
- **耗时取重复测量的中位数**，不取单次、不取 min/max；同量级比较必须在**同一份二进制**内用开关做 A/B
  （跨进程/跨构建会带 ±2% 以上的系统性偏差）。
- **产物必须逐字节一致**（md5 / `SequenceEqual`），除非改动本身就是有意的算法变更。
- **评价性能改动先算封死性上界**：把可疑段落「全部做成零耗时」最多能拿多少，
  比先写 SIMD 再测快得多，也能直接判定方向值不值得投入。
- **基准不预热、迭代 1 次（最多 2 次）**；大图（143 MP）单次测量是噪声，必须交错多轮取中位数。
- 「改动前」不得用**手写参考实现**充当，必须用 `git archive` 取真实历史提交编成独立程序集，
  在同一进程内与当前实现交错 A/B。历史上手写参考测出的 Resize/EXIF 加速比全部偏高（已作废），
  教训是参考实现比真实旧代码更慢会放大加速比。
- 不同机器之间不可比：`docs` 与历史报告里出现的 143 MP JPEG 编码 303 ms 来自另一台工作站。

| 格式 | 项数 | 几何平均提速 |
|---|---:|---:|
| jpeg | 18 | **7.86x** |
| rgb24（缩放） | 21 | **2.61x** |
| gray（灰度） | 5 | 2.54x |
| gray8 | 7 | 1.86x |

合计几何平均 **1.99x**，输出字节完全一致 105/123。18 项差异**全部是 GIF**：默认量化器从
Wu+Floyd–Steinberg 换成 Octree+Bayer 的算法变更（彩色 GIF +2.5%~+45%，灰度 GIF +54%~+122%），
属体积上的取舍而非性能问题。

已知干扰项：143 MP 的 WebP 编码对**内容极度敏感**——两版解码输出仅差 0.051/255，
同一二进制编码两份像素的耗时却是 32 s vs 8 s。因此大图档的非解码项一律改用固定 raw 像素作输入。

## 4. 已否决 / 勿重复尝试（汇总）

| 方向 | 实测 | 原因 |
|---|---|---|
| **AVX-VNNI 量化 resize** | **缩小 0.25x（慢 4.0 倍）、放大 0.56x（慢 1.8 倍）** | 见下方说明 |
| GIF 量化（直方图/矩/切分/LUT）SIMD | 端到端上界仅 6.1%，实际可向量化面 1.4% | 90.8% 的耗时在抖动的串行依赖链 |
| GIF 抖动去边界检查 / 向量化 | 指针版反而慢 2%；链长缩短不了 | 延迟受限，非吞吐受限 |
| GIF LZW 解码「直写输出」 | lzw 1.07x，性能提升不理想，已回退 | 输出阶段仅占 LZW ~10% |
| GIF LZW 解码位缓冲/打包/二级跳转表 | −4% ~ −12% | 见 §4.1 |
| JPEG produce 按行带多生产者并行 | 303 → 921 ms（dop=∞）、572 ms（dop=4） | 队列争抢 + 乱序入队让 Huffman 冷读 |
| JPEG 批继续加大到 256 | 略差于 64/128 | 在途工作集变大 |
| PNG 换更强滤波器降熵 | Paeth 慢 32% 只小 6%，Average 更差 | Up 已是速度/体积最优折中 |
| PNG 编码阶段 SIMD（滤波） | 无效 | deflate 占 PNG 编码约 94% |
| Adler32 加速 PNG 解码 | 0% | 解码走 BCL `ZLibStream`，不经本库 Adler32 |
| `AddBytesInPlace` 继续优化 | 4 MB 2.8x → 409 MB 1.10x | 纯带宽搬运，出缓存即封顶 |
| 量化表缓存 | 无可测收益 | 每次编码只建 64 字节的表 |
| 把 4×4 块和提到循环外预计算 | JPEG +9.3 ms、PNG −10.4 ms，净亏 | 位一致但方向不稳 |

**AVX-VNNI 说明**：Resize 本质是浮点插值，套 VNNI 必须走量化路径（int8 源 + 定点权重）。
点积本身 VNNI 确实快（16384 维 int8 点积标量 0.5 → VNNI 11.6 GMAC/s，约 24x），
但 resize 的瓶颈是**逐像素 gather + 内存带宽**，不是乘加：实测 143 MP
缩小 bilinear 140 → 556 ms、放大 bicubic 952 → 1705 ms，量化误差虽只有 1~2 级，
速度却是负提升，代码已撤销。同一结论适用于 ARM 的 `UDOT/SDOT`（同类整型点积指令）。

### 4.1 GIF LZW 解码为何无法再快

432 万像素图的结构计数：码数 863,497、前缀链步数 4,880,199（5.65 步/码）、补位迭代 1,216,130；
串长 >16 的只占 2.8% 的串，却覆盖 49% 的像素。消融实测（同二进制切换探针，产物全部一致）：

| 变体 | lzw 中位 | 相对基线 |
|---|---|---|
| 基线（>16 走 SSSE3 `pshufb` 反序） | 12.76 / 12.92 ms | — |
| 输出**全部**走标量 | 13.80 ms | +0.9 ms |
| **完全跳过输出阶段** | 11.48 ms | −1.3 ms |
| SIMD 反序**下探到 len≥5** | 13.51 ms | **+0.5 ms（更慢）** |

⇒ 输出阶段只占 10%，其余 90% 是「变长位域串行解包 + `code = prefix[code]` 指针追逐」，
指令级不可向量化。要提速只能改算法（减少链步数/解包次数）。

## 5. JPEG

### 5.1 分阶段与封死性上界（143 MP）

| 阶段 | 编码 | 解码 |
|---|---|---|
| total | 331 ms（同日复测 303） | 440.5 ms |
| 单线程关键阶段 | produce 302.7（busy 241）/ huffman 330.7（busy 218） | entropy 176.8 / reconstruct 255.1 |
| 并行阶段 | dct-wall 2646 ms ÷ 8 worker（占空比 11%） | idct-color 231.5（单线程） |

结论：FDCT+量化并行且不在关键路径，免费也拿不到 1% ⇒ 动它无意义；
解码 reconstruct 单线程占 58% ⇒ 上界 40%+（已落地）；
编码被 produce（色彩转换，占 total 64.5%）与 huffman 双重单线程约束，只有动其中之一才有端到端收益。

### 5.2 已落地

- **解码重建按 MCU 行并行**：decode total 440.5 → 223~229 ms，reconstruct 255 → 37.5~45.7 ms。
- **`McuBatchSize` 16 → 64**：批 16 时在途仅 256 个 MCU，produce-wait 61.8 / huffman-wait 90 ms 全是饿等；
  加深后两个 wait 掉到 ~10 / ~21 ms。
- **按图优化 Huffman 表**（`JpegEncoderOptions.OptimizeHuffman`，默认开）：搜索期改用标准表，
  赢家再按最终设置补编一次，**产物逐字节不变**，两遍编码代价约 1.9~2.4x 省 20%~40% 体积。
- **搜索期 4:2:0 单遍**：判定只看解码像素，Huffman 表不影响系数，选中 q 与用哪张表无关。

### 5.3 剩余瓶颈

- 解码：entropy 占 77%（177/229 ms），逐位变长位流 + 依赖链，单 scan 内不可并行；
  progressive 必须全扫描完成才能重建。RST 分段并行只对带 RST 的 baseline 图有效，语料未见。
- 编码：produce（fill ~190–240 ms，已 SSSE3，AVX2 对 3 字节像素去交错无干净方案）与
  huffman busy（LUT 已覆盖）是两个 ~200 ms 级地板；单动一个上界 ≈ −25~30%，两者都动才有 −50%。
  若还要再拿，方向是把 Huffman 也并行（按 MCU 行分片、各自重启 DC 预测、拼接多个 SOS），**未做**。

## 6. PNG / BMP

- **解码反滤波**：原为逐字节 `switch` + 「整行 `CopyTo` 再原地改」，改为按滤波器类型分派 +
  `src` 直读直写 `dst` + Paeth 代数化简。**Paeth 不可跨像素前缀化**（左邻 `a` 取自本行已重建的前一字节，
  三路比较非线性）；可向量化的维度只有 `bpp` 条互不相干的链，而每步都要截断 ⇒ 只能按链长迭代，
  bpp 越小越吃亏（bpp=1 时比标量还慢）。设计已完成、待基准，见 [SimdPitfalls.md](SimdPitfalls.md) §3。
- **编码瓶颈是 deflate**：143 MP 图 PNG 编码 2106 ms vs JPEG 303 ms；BMP 做同等量级行处理只要 132 ms
  ⇒ deflate 约占 94%。换滤波器实测否决（3000×2250 RGB，zlib level 6）：

  | 滤波器 | deflate 耗时 | 输出体积 |
  |---|---:|---:|
  | None | 280 ms | 7.99 MB |
  | **Up（当前）** | **521 ms** | 5.00 MB |
  | Sub | 620 ms | 4.87 MB |
  | Paeth | 690 ms | 4.69 MB |
  | Average | 702 ms | 4.61 MB |

- **`ApplyUpFilterSimd` 已改掉 `new Vector<byte>(span.Slice(i))`**（每步都带边界检查与拷贝），
  改为 `Vector.LoadUnsafe` 按偏移直接载入；`JpegEncoder` 里同类问题也已一并处理。
- **BMP**：行填充按位对齐、RGB→BGR `pshufb`、分级行缓冲（stackalloc / ArrayPool）均已落地。
- **口径提醒**：16 位灰度 PNG 降 8 位时本库取高字节（`v >> 8`，标准做法），
  Pillow 的 `I;16` 是截断到 255，两者结果不同，**不要拿 Pillow 当 16 位 ground truth**。

## 6.5 WebP 解码（纯托管 VP8L vs libwebp）

口径：同一进程、每个实现 warm 5 / iter 10 取最小值，`TieredCompilation=false`，Release。
正确性全部逐像素 bit-exact（无损 8/8 样本，含 143 MP、1×1、1×512、alpha、2.3 MB 噪声）。
**同机不同时段整体负载会让所有数字一起漂移 ±30%（143 MP 另一次跑是 2644 / 2520 ms），
所以只看同一行的两列比例，不要跨行比较绝对值。**

| 场景 | libwebp | 托管（优化后） | 优化前 |
|---|---:|---:|---:|
| 照片 1000×1000 无损 | 14.0 ms | 14.0 ms | 19.3 ms |
| 渐变 1920×1080 无损 | 16.1 ms | 16.0 ms | 17.1 ms |
| UI 1600×1200 无损 | 3.5 ms | 3.3 ms | 3.4 ms |
| 噪声 1024×768 无损 | 9.8 ms | 9.2 ms | **101.8 ms** |
| alpha 1024×1024 无损 | 10.0 ms | 10.3 ms | 11.3 ms |
| 143 MP 无损 | 1888 ms | 1905 ms | 2468 ms |

- **两个真瓶颈，与"托管代码天然慢"无关**：
  1. `LsbBitReader` 每读 1 bit 都做一次边界检查并推进游标；改成 64 位缓冲 + 4 字节 refill 后，
     位读取从「每 bit 一次分支」变成「每 32 bit 一次」。
  2. `HuffmanTable.DecodeSymbol` 原为「逐位读 + 每层线性扫该码长的所有码字」，最坏 O(码长 × 候选数)。
     改成 8 bit 一级表后，符号解码 = 1 次 peek + 1 次数组索引。**噪声图 14.9x 的差距基本全部来自这里**：
     噪声的符号分布平坦、码长接近 8，正好踩在逐位+线性扫描的最坏情况上。
  3. 建表方向易错：VP8L 码字按 MSB-first 写出、位流按 LSB-first 读入，所以表索引是
     `reverse(code, len)` 的低 `len` 位，按 `2^len` 步长铺满；写成直接索引会「看起来能跑、画面全错」。
- **内存**：`uint[] argb` + `byte[] 输出` 两份整幅曾让 143 MP 峰值分配到 1117.7 MB（输出本身 545.5 MB）。
  改为把调用方缓冲区同时当 ARGB 工作区（`MemoryMarshal.Cast`）+ 末尾原地 ARGB→RGBA 交换后，
  分配降到 550.9 MB；另补 `WebpContainer.Load(byte[])` / `DecodeRgba(byte[])` 零拷贝重载，
  去掉每次解码的整文件 `ToArray()`（24 MB 的 143 MP 文件白拷两次：分派判动图一次、解码一次）。
- **结论**：VP8L 解码已可与 libwebp 持平，纯托管替换在这一段没有性能理由反对；
  真正挡住"去掉 libwebp"的是有损 VP8 解码与全部编码路径。

## 6.6 WebP SIMD 与算术编解码优化（2026-11-03）

本轮先保存**当时工作区**的 Release 程序集作为基线（包括已有、尚未提交的编码器改动），
再用 `dotnet-trace` 对有损编码、有损解码和无损编码分别采样。不是与 Git HEAD 比较，
也不是与 libwebp 比较；§6.5 是历史记录，不能代表本轮代码的覆盖范围或性能。

环境：Windows x64，Intel Core i7-10750H，.NET 10.0.14，Release，
`TieredCompilation=false`。测试工具为 `tools/perf/WebpProbe`：
照片来自 `examples/5_star_base.jpg` 的确定性最近邻采样；其余为固定的渐变、UI 色块、
固定种子噪声和含 alpha 的渐变，均为 512×512，有损质量为 75。
基线程序集通过独立 `AssemblyLoadContext` 加载，和候选版本在同一进程中交替运行。
每项预热 3 次，测量 11 批、每批按约 30 ms 选择 1～64 次调用，报告中位数。
耗时包括输出分配；开始计时前逐字节比较两版输出，CSV 同时记录大小和 SHA-256。

### 热点与保留的修改

- 有损编码采样中，模式试算、系数写位、正 DCT 是主要热点；不能把整条路径的时间
  都归因于像素转换。本轮将 4×4 正 DCT/WHT 改为四路 int32 SIMD，保留原标量实现，
  使用相同的定点乘法和舍入规则，通过现有 SSE/NEON 兼容层转置寄存器。
- 解码采样主要落在布尔位读取、跨行滤波和 YUV 上采样，IDCT 的占比较小，因此
  本轮没有优先改 IDCT。跨行滤波改为 8×8 字节向量转置，替换逐字节收集和散写；
  YUV 上采样的偶/奇像素交织改用寄存器 unpack，替换栈缓冲区写入、重读和 shuffle。
- 算术编码器和解码器的归一化用前导零计数一次求出移位量，替换逐位循环。
  解码端仍保持相同的字节补充位置和 EOF 语义。这部分收益来自减少串行操作，属于
  SIMD 之外的优化。
- 无损采样的主要热点在 LZ77 搜索和统计。曾测试批量比较匹配像素：渐变编码约快 7%，
  但照片和噪声约慢 3%～4%，因此撤回；最终未修改 VP8L 编解码路径。

| 内容 | 编码前 | 编码后 | 编码耗时降低 | 解码前 | 解码后 | 解码耗时降低 |
|---|---:|---:|---:|---:|---:|---:|
| 照片 | 118.644 | 113.230 | 4.6% | 7.687 | 7.351 | 4.4% |
| 渐变 | 57.392 | 53.378 | 7.0% | 3.310 | 3.079 | 7.0% |

独立内核测试：DCT 200,000 次由 6.509 ms 降到 2.821 ms（2.31×），
WHT 200,000 次由 20.168 ms 降到 1.270 ms（15.89×），跨行滤波 100,000 次由
14.196 ms 降到 13.077 ms（1.09×）。滤波微基准反复处理同一缓冲区，代表热缓存下的
内核开销；端到端收益以上表为准，不能用内核倍率代替整条编解码流程的倍率。

未修改的无损路径作为对照：本次测量倍率在 0.95×～1.01× 之间波动，
不宣称有无损加速收益。结果仅覆盖本机和上述样本；ARM64 的兼容实现已接入，
尚未在 ARM64 真机测量，不能据此声称跨平台有相同收益。

### 正确性与复现

- 255 项 WebP/VP8 测试全部通过，含 libwebp 对拍和新增的变换逐项一致性、
  滤波未修改区域、奇偶尺寸上采样、概率端点、字节补充和截断 EOF 测试。
- `DOTNET_EnableHWIntrinsic=0` 时，37 项 SIMD/归一化/VP8 编码回退测试全部通过。
- 5 类样本、4 条路径共 20 项输出与基线逐字节一致：有损和无损编码字节不变，
  两种解码的 RGBA 像素不变。Release 构建无警告、无错误。

## 6.7 WebP 第二轮：压缩率与流式解码（2026-11-05）

测量台为 `.perf/QualityProbe`：6 类 1024×1024 语料（photo / ui / grad / a_text /

### 有损压缩率（trellis + 4 段分段 + 滤波 RD）

24 组合计：我方 1,066,296 B，libwebp 1,249,300 B（**0.853×**）；同一测量台的

### VP8L 无损多 pass

首遍统计完成后用**实际码长**（`ChannelBits` 对每个通道的真实写入位数 +
`MetaImageBits` 的组图开销）重算 Huffman，再以 2 轮精化（`MaxRefinePasses=2`）

小图保持零额外开销。libwebp 无损码流交叉验证：双方解码均与源 RGBA bit-exact

3562 → 3540（−0.62%）；photo/ui/grad/rgba_panel 不变。**未达 −2% 目标**：
剩余差距主要在 predictor 选择、分组聚类与码表写出，静态像素熵模型对贪心 LZ77
已接近最优，单靠码长重算无法再挤出 2% 量级。

## 6.8 WebP 编码效率三处热点：trellis / 估算走查 / 分配（2026-11-06）

### 口径

- **与 libwebp 的差距**：`.perf/GapProbe`（1024² × photo/gradient/ui/noise/alpha，
  q75），托管与原生 DLL 同进程交替、预热后取中位数，同时记录每调用分配量。
- **改动收益**：`.perf/AbProbe` 同进程交错 A/B（11 轮取中位数），基线是
  `git archive HEAD` 构建的程序集——会话开始时编码路径与 HEAD 逐字节一致，
  因此 HEAD 是干净对照（解码侧有会话前未提交的行流式改动，本次未动解码）。
- **正确性**：全部编码输出与 HEAD **逐位一致**（10/10 组 sha256 相同）；
  trellis 另做了 20000 组随机块 fuzz，levels/slots/last 与旧实现完全相等；
  750 项全量测试通过（含 libwebp 编解码对拍）。

### 三个热点与改动

1. **有损：`Vp8Trellis.Quantize` 占编码采样 56%**（dotnet-trace，改前）。改写：
   空档代价从「每个 n 重算整段（O(n²) 次 BitCost 查询）」改为每块一次的
   h0/h1 + 零游程前缀和，内层 O(1) 取差；`BuildCandidates` / `NonZeroCost` /
   量化误差平方从「每个状态」提到「每个位置」；`Vp8CostTable` 二维表展平
   （热路径单次边界检查）。内核基准 65536 块 492.6 → 150.1 ms（**3.28×**），
   fuzz 逐位等价，端到端有损编码 1.21~1.69×（见下表）。
2. **无损：predictor 模式 LZ77 复评对每个候选跑「首遍 + 2 轮精化」的整图走查**
   ——photo 上 8 个候选 ≈ 24 遍完整走查，曾占无损编码的大部分耗时。改动：
   估算路径（`EstimateTokenBits`）只跑首遍（`refine: false`），精化轮只保留在
   最终候选之间的体积择优；>1MP 才切横带排序 + 前 2 名整图复评
   （`PlanBandPixels`/`PlanFullReevalPixels`）。估算首遍与精化同口径（所有候选
   一致），实测 5 类内容输出仍与 HEAD 逐位一致。
3. **无损编码每次调用分配 400~500 MB**（1024²，图像本身 4 MB；含 alpha 的有损
   编码 594 MB）：token 缓存（`Token[width*height]` × 每候选）、LZ77 链/哈希表
   （~4.5 MB × 每遍）、代价模型前缀和（4 MB × 每模型）反复新建。新增线程静态
   LIFO `BufferPool`（`EncodeTokenStream` / `EstimateTokenBits` 结束时按快照回退；
   子图像编码嵌在外层 token 流里，必须按栈序释放），color cache 与前缀 [0]
   显式清零保证与新分配等价。

AbProbe 同进程交错 A/B（HEAD → 当前，**输出逐位一致**）：

|---|---:|---:|
| photo | 1.59× | 1.78× |
| gradient | 1.44× | 1.34× |
| ui | 1.62× | 1.11× |
| noise | 1.69× | 1.40× |
| alpha | 1.21× | 1.39× |

GapProbe 托管 / libwebp 比值（同进程，1024²，改前 → 改后）：
有损 7.57/5.67/4.86/10.41/3.97 → **5.38/4.65/4.27/7.05/3.48**；
无损 8.23/2.52/3.66/19.86/2.90 → **4.85/2.22/2.65/16.36/2.33**

分配量（每调用，1024²）：无损 photo 310 → **104 MB**、noise 356 → **142 MB**、

### 仍存在的差距（结构性，本轮未动）

- libwebp 每次编码是「1 次哈希链填充 + 直方图遍 + 写出遍」；我方无损是
  「predictor/配置候选枚举 ×（首遍 + 精化 + 写出）」，有损是「i4x4/16×16 双路
  RD + trellis + 两遍概率」。这些固定开销换来的是压缩率（有损 0.853×、无损与
  libwebp 持平），属设计取舍而非实现缺陷。
- noise 无损仍 ~16×：不可压内容把「多候选 × 多遍走查」的固定开销放大到极致。
- 可继续的方向（均会改变输出，需单独标定）：pass2 重放直接复用 pass1 量化电平
  （跳过第二次 trellis，预计有损再 −20~25%）；plan/配置候选裁剪；估算走查的
  哈希链结果跨候选复用。

### 已否决

- **≤1MP 用横带估算 predictor 排序**：横带对长周期内容（重复周期 > 横带行数）
  会漏掉长距离重复并排错序——实测 x^y alpha 无损体积 2332 → 6058 B（+160%），
  横带加宽到 1/4 图仍复现；弃用，只保留 >1MP 的横带路径（与 HEAD 行为一致）。
- **估算去掉精化轮**：实测 5 类内容输出不变（精化只影响最终候选择优，不影响
  估算排序），保留为正式改动。

## 6.9 WebP 有损量化口径对齐（2026-11-09）：完整档 +2.9%、快档 +16%

### 口径

- **耗时**：`.perf/TimeProbe`（只用公开 API，因此可在 HEAD 工作树里直接跑同一份代码），
  1280×853 `examples/scene.png`，每档预热 1 次 + 15 次取样取**最小值**（本机
  逐次波动可达 ±10%，中位数不可靠），HEAD 与当前**交替 3 轮**：`58.8/58.9/59.6`
  这类同轮一致性才算可信。
- **压缩率**：`.perf/QualityProbe`（1024² × 7 类内容 × q50/75/90/95，method 6），
  与改动前的 HEAD 逐组对照。

### 改动与代价来源

量化路径新增了 libwebp 的三项口径（`docs/WebpEncoder.md` §3.8）：按系数类型的量化偏置、
亮度 AC 频率锐化、DC 电平按 `(dc+4)>>3` 的真实重建量择优。每系数只多一次乘加与一次
表查询，但它在**每个**系数上都要做（1280×853 约 1.7M 系数 × RD 双路 ≈ 5M 次）：

| 档位 | HEAD | 当前 | 变化 | 输出体积 |
|---|---:|---:|---:|---|
| method 6, q75 | 597.6 / 600.6 ms | 615.0 / 620.2 ms | **+2.9%** | 97,962 B（不变） |
| method 4, q75 | 58.8 / 59.6 ms | 68.5 / 68.5 ms | **+16%** | 109,108 → 101,886 B（**−6.6%**） |

完整档只摊到 3%，因为 trellis 的 DP 本身就是重活；快档靠标量量化，10 ms 的绝对增量
占满 60 ms 的预算，所以比例很大——但同一档位下体积也降了 6.6%，属于 RD 曲线上的平移
而不是纯损失。

### 顺带做掉的两处（输出与改前逐位一致）

1. **量化改 `QUANTDIV` 定点乘加**：原实现是「半格定点除法 + 两次取整校正 + 偏置校正」，
   现按 libwebp `(n*iQ + B) >> QFIX`（`QFIX = 17`、`iQ = (1<<17)/dq`、
   `B = bias << 9`）一次算完。24 组语料输出**逐位一致**（`iQ` 截断误差在本语料上
   未跨过任何判定边界）。
2. **DC 择优 3 候选 → 2 候选**：`DcRecon` 随电平单调不减、单电平至少挪 `dq/8 ≥ 0.5`
   个灰度级，所以最优必在 `floor(|c|/dq)` 与 `+1` 之间，不必展开 `q±1` 的循环。
   同样逐位一致。

两项都没能把快档的 +16% 吃回来（量化本身已经不是瓶颈，增量在频率锐化与偏置的
每系数开销上）；若要继续，方向是把亮度 AC 的锐化与偏置折进 dq 的等价步长
（`dq' = dq` + 偏置用固定 B），但那会与 libwebp 的 `zthresh` 语义产生偏差，需要单独验证。

## 8. 方法论沉淀

- **先量化工作量，别靠猜**。GIF 解码加临时计数器后才发现：先前假设「前缀链 432 万次串行 load
  是瓶颈」，实测只有 331 万步，据此设计的二级跳转表白做。
- **快路径不要加罕见边界判断**：每像素多一次 `idx < writeLen` 判断，就能把 +8% 变成 −4%。
- **探针代码本身会拖慢基线**：加 4 个探针分支后 lzw 基线由 12.0 → 12.9 ms（+7%）。
- **指令数比不能当立项依据**：27 条 ALU 换成 1 条指令，实测反而更慢（见 ArmFindings.md §8.2）。
- **跨构建 A/B 分不出细分量级的信号**：2% 以内的差异一律用同二进制静态开关复测。

## 9. WebP 编码器：按 libwebp 标准实现的性能对齐（2026-11-07）

目标：既提性能又对齐参考实现；只在默认快档（method ≤ 4）改变行为，完整档逐位不变。

| 改动 | libwebp 对应 | 输出影响 |
|---|---|---|
| `IsDirectEntropyBest`：抽样统计 direct / pix_diff / subtract-green 熵，加变换头惩罚后判定 `kDirect`，命中即跳过整条空间变换链 | `src/enc/vp8l_enc.c:108-256 AnalyzeEntropy()`、`:1589-1601` 三个 `use_*` 开关 | 仅高熵（噪声）图变化 |
| 14 模式残差直方图改「分块预取像素 + 按模式批量累加」 | `src/enc/predictor_enc.c:451 ComputeResidualsForTile()`、`VP8LPredictorsSub[mode]` | 逐位不变 |
| 量化用 `ceil(2^32/dq)` 定点倒数 + 一次校正替代逐系数 `idiv` | `src/dsp/quant.h` 预展开量化矩阵、`enc_sse2.c:1514 QuantizeBlock_SSE2` | 逐位不变 |
| 规范码建表时预反转；位流 64 bit 累加、满 32 bit 一次写 4 字节 | `huffman_encode_utils.c:385-411 ConvertBitDepthsToSymbols()`、`bit_writer_utils.h:147 VP8LPutBits()` | 逐位不变 |

实测（`.perf/EffortProbe`，1024² 5 类样本，与 libwebp 简易 API 同口径）：

- 同进程交错 A/B（5 轮中位，`SIC_WEBP_NO_DIRECT_BAIL` 开关）：纯噪声无损
  **142.22 → 100.96 ms = 1.41×**；其余四类 0.98~1.02×（无回归）。
- 跨进程 ratio：noise lossless **1.49 → 1.06**（绝对 143.98 → 101.52 ms），
  photo lossless 0.92 → 0.71，其余档位持平。
- 位流：除 `noise/lossless` 的 fast 档外，**9 组 fast_sha 与全部 11 组 full_sha 均与基线一致**；
  noise 体积 3,145,826 → 3,145,822 B；全部产物经托管解码器 + libwebp 双解码一致。
- Release 0 警告 0 错误，全量 **753 例通过**（1 例缺本地语料跳过）。

两处由同进程 A/B 推翻理论推断的教训：

- 「一次遍历同时累加 14 份 4 KB 直方图」会让 56 KB 直方图交替写、撑爆 L1：
  photo +4% 但 gradient −9% / ui −4%，净负；改成按模式分块写热直方图后回到中性（0.99~1.01×）。
- 熵分析本身会拖慢结构化图（gradient −11%），需 4096 像素预筛；且阈值必须按
  **活跃通道**归一化——不透明图的 A 通道熵恒为 0，用四通道总熵会把纯噪声
  （RGB 各 8 bit、共 24 bit/像素）误判成可压缩，导致 bail 完全不触发。
