## 实测验证：examples/progressive.jpg（10650×13426 = 143 MP，RGB 409 MB）

### 方法

- "改动前"不是手写参考实现，而是用 `git archive` 取出提交 `7f967ba` 的 `src/` 编成独立程序集
  （`AssemblyName=SharpImageConverter.Baseline`），与当前工作树的 `src` 通过 `extern alias` 同时加载，
  在同一进程内交错 A/B、每侧取多轮最小值。此前用**手写参考实现**测出的数字偏高，已作废（见下）。
- 非原地算子（Resize/EXIF/编解码/格式转换）直接吃同一份输入，零额外开销；
  原地算子（Grayscale、AddBytesInPlace）每轮先无分配拷贝到预分配暂存区——**不能用 `Clone()`**，
  大数组克隆本身触发 LOH GC，扣除项自带巨大噪声（会让结果变成负数）。
- 合计 40 项，全部 `SequenceEqual` 逐字节比对：不一致 0 项。
- 环境：.NET 10.0.12 / 12 逻辑核 / SSE2+SSSE3+SSE4.1+AVX2 均可用。

### 读数说明

- **ResizeBilinear 是这轮最大赢家**，放大/缩小都稳定在 2.1–2.3x（SSSE3 路径真正吃满了）。
- **编解码整体几乎不动**：JPEG 解码 1.00x（未改）、PNG 编解码 ~1.0x、JPEG 编码 ~1.0x。
  因为耗时被熵编码/deflate 主导，`AddBytesInPlace` 和量化表缓存再快也占不到 1%。
  PNG 编码的 0.99x 不是回退——写入端 `PngWriter.ApplyUpFilterSimd` 未经改动，是测量顺序偏差。
- **`AddBytesInPlace` 的收益随缓冲变大而坍缩**：4 MB（进缓存）2.8x → 12 MB 1.20x → 409 MB 1.10x。
  它做的是纯带宽搬运，超出缓存后被内存带宽卡死。
- **量化表缓存没有可测收益**：每次编码本来只建 64 字节的表，缓存省不掉可观时间。

## GIF LZW 优化实验记录（2026-09-25）

测试图 2400×1800 = 432 万像素，`--gif-bench 15` 取**中位数**。
准入阈值：**提升不足 10% 算作无效提升，不保留**。

### 已保留：LZW 编码字典查找 1.37x

| 阶段 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 编码 total | 86.79 ms | 79.52 ms | 1.09x |
| └ lzw | 28.998 ms | 21.189 ms | **1.37x** |

根因是真实的算法缺陷：原哈希 `h = (c << 4) ^ ent` 中 `c ≤ 255`、`ent < 4096`，
故 `h` 恒落在 `[0, 4095]`——8191 个槽位只用到一半，**装载因子实际为 1.0**，
开放寻址的探测链严重退化。

改为 64 位乘法散列（`0x9E3779B97F4A7C15`）+ 32768 槽位（装载因子 0.12）+ 线性探测，
槽位打包为 `((fcode+1) << 12) | code`，键与值同处一条 cache line。
槽位数扫过 4096→131072，32768 最优；256 KB 超过 LOH 阈值，故从 `ArrayPool` 租用，
避免动画逐帧触发大对象 GC。

**踩过的坑**：32 位放不下（20 位键 + 12 位值 + 1 位占用标记 = 33 位）。
第一版用 `uint` 打包并以 0 表示空槽，结果 `fcode == 0`（即 `c=0, ent=0`）
时空槽被误判为命中，输出 md5 对不上。改用 `ulong` 存 `fcode + 1` 才干净。

### 已回退：LZW 解码「直写输出」1.07x（低于阈值，按规则不保留）

新增 `strLen` 串长表，展开前即可确定串长，字符按位置直接写进输出缓冲，
省掉原先「压栈 + 反向拷贝」的第二遍（原实现每像素写两次）。
实测 LZW 阶段 12.875 → 12.025 ms（**1.07x**）、解码 total 15.04 → 14.06 ms（1.07x），
**未达 10% 阈值，已回退**至优化前实现（解码 LZW 恢复为 12.691 ms）。

### 实测否决的解码改动（勿重复尝试）

在量化出真实工作量后逐一验证，均为负收益：

| 改动 | 实测 | 原因分析 |
|---|---|---|
| 位缓冲一次补 4 字节 | −4% ~ −12% | 补位迭代从 142 万降到约 36 万，但分支与拼装开销抵消了收益 |
| `prefix`/`suffix` 打包成单个 int | −5% | 打包后下一跳地址要等 load + 移位；拆成两个数组时两次加载地址相同、可并行发射 |
| 二级跳转表一次展开两像素 | −5% | 链步数没有预想的多，额外表的维护成本大于收益 |

### 教训：先量化工作量，别靠猜

加临时计数器后测出真实分布（432 万像素图）：
**码数 100.7 万、串平均长 4.29、前缀链迭代 331 万、位补位迭代 142 万**。
先前假设「前缀链 432 万次串行 load 是瓶颈」错了近一半，据此设计的二级跳转表白做了。

另有两个方法论要点：

- **控制实验**：某段时期每次改动都稳定慢 4%，怀疑是环境噪声。
  把解码器还原成基线代码后两侧等速，才确认是真实回退——
  根因是快路径里每像素多了一次 `idx < writeLen` 判断，
  把罕见截断拆成慢路径后才由 −4% 转为 +8%。**快路径不要加罕见边界判断**。
- **产物一致性**：所有改动均以编码/解码产物 md5 逐字节一致为验收条件，
  并另用 7 张不同内容/尺寸图（1×1 到 2000×1500）做往返验证。
