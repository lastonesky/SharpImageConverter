## GIF LZW 优化实验记录（2026-09-25）

测试图 2400×1800 = 432 万像素，`--gif-bench 15` 取**中位数**。
准入阈值：**提升不足 7% 算作无效提升，不保留**。

### 已保留：LZW 编码字典查找 1.37x

| 阶段 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 编码 total | 86.79 ms | 79.52 ms | 1.09x |
| └ lzw | 28.998 ms | 21.189 ms | **1.37x** |

根因是真实的算法缺陷：原哈希 `h = (c << 4) ^ ent` 中 `c ≤ 255`、`ent < 4096`，
故 `h` 恒落在 `[0, 4095]`——8191 个槽位只用到一半，**装载因子实际为 1.0**，
开放寻址的探测链严重退化。

改为 64 位乘法散列（`0x9E3779B97F4A7C15`）+ 32768 槽位（装载因子 0.12）+ 线性探测，
槽位打包为 `((fcode+1) << 12) | code`，键与值同处一条 cache line。
槽位数扫过 4096→131072，32768 最优；256 KB 超过 LOH 阈值，故从 `ArrayPool` 租用，
避免动画逐帧触发大对象 GC。

**踩过的坑**：32 位放不下（20 位键 + 12 位值 + 1 位占用标记 = 33 位）。
第一版用 `uint` 打包并以 0 表示空槽，结果 `fcode == 0`（即 `c=0, ent=0`）
时空槽被误判为命中，输出 md5 对不上。改用 `ulong` 存 `fcode + 1` 才干净。

### 已回退 / 待重新评估：LZW 解码「直写输出」1.07x（旧 10% 阈值下低于门槛；新 7% 阈值下 1.07x = +7% 已达标）

新增 `strLen` 串长表，展开前即可确定串长，字符按位置直接写进输出缓冲，
省掉原先「压栈 + 反向拷贝」的第二遍（原实现每像素写两次）。
实测 LZW 阶段 12.875 → 12.025 ms（**1.07x**）、解码 total 15.04 → 14.06 ms（1.07x），
**按旧 10% 阈值未达标，已回退**至优化前实现（解码 LZW 恢复为 12.691 ms）。
  **按新 7% 阈值，1.07x = +7% 现已达标，应重新评估是否恢复（须先确认产物 md5 逐字节一致）。**

### 实测否决的解码改动（勿重复尝试）

在量化出真实工作量后逐一验证，均为负收益：

| 改动 | 实测 | 原因分析 |
|---|---|---|
| 位缓冲一次补 4 字节 | −4% ~ −12% | 补位迭代从 142 万降到约 36 万，但分支与拼装开销抵消了收益 |
| `prefix`/`suffix` 打包成单个 int | −5% | 打包后下一跳地址要等 load + 移位；拆成两个数组时两次加载地址相同、可并行发射 |
| 二级跳转表一次展开两像素 | −5% | 链步数没有预想的多，额外表的维护成本大于收益 |

### 教训：先量化工作量，别靠猜

加临时计数器后测出真实分布（432 万像素图）：
**码数 100.7 万、串平均长 4.29、前缀链迭代 331 万、位补位迭代 142 万**。
先前假设「前缀链 432 万次串行 load 是瓶颈」错了近一半，据此设计的二级跳转表白做了。

另有两个方法论要点：

- **控制实验**：某段时期每次改动都稳定慢 4%，怀疑是环境噪声。
  把解码器还原成基线代码后两侧等速，才确认是真实回退——
  根因是快路径里每像素多了一次 `idx < writeLen` 判断，
  把罕见截断拆成慢路径后才由 −4% 转为 +8%。**快路径不要加罕见边界判断**。
- **产物一致性**：所有改动均以编码/解码产物 md5 逐字节一致为验收条件，
  并另用 7 张不同内容/尺寸图（1×1 到 2000×1500）做往返验证。

## SIMD 可行性分析：编码量化 vs 解码 LZW（2026-09-25）

**提问**：编码的量化过程、解码的 LZW 过程能否通过 SIMD 提升性能？阈值：提升 <7% 视为无效。

**结论：两者（SIMD 方向）都拿不到 ≥7%（已按现行 7% 阈值复核）；量化侧在数学上被封死（端到端编码最多 6.1% < 7%），解码侧可向量化面只有约 1 ms（< 7%）。**

### 1. 编码量化：不可行（双重封死）

#### 1.1 子阶段实测（抖动开启，quantize 中位 59.5 ms）

| 子阶段 | 中位耗时 | 占 quantize | SIMD 可行性 |
|---|---|---|---|
| `BuildHistogramParallel` | 3.2 ms | 5.4% | ✗ 数据相关下标**散布累加**（5 个数组），AVX2 无 scatter |
| `CalculateMoments` | 0.17 ms | 0.3% | 太小，无意义 |
| `Split` 中位切分 | 0.28 ms | 0.5% | 太小，无意义 |
| `BuildMappingLut` | 1.1 ms | 1.8% | ✓ 理论可 AVX2（35937 格 × ≤256 色距离） |
| **`ApplyDitheringWithLut`** | **~54 ms** | **90.8%** | ✗ 见 1.3 |

交叉验证：`--dithering off` 时 quantize 只有 **6.375 ms**，即抖动独占 53 ms。

#### 1.2 封死性上界（不需要写代码就能判定无效）

即便把直方图/矩/切分/LUT **全部**做到零耗时（保底 4.75 ms = 3.2+0.17+0.28+1.1）：

- quantize：59.5 → 54.8 ms，最多快 **8.0%**（达 7% 单阶段阈值，但端到端编码仅 6.1% < 7%，按「单阶段提速但端到端未达标按无效处理」仍不保留）
- 编码总耗时：78.2 ms，最多快 **6.1%**

而其中真正可向量化的只有 `BuildMappingLut` 的 1.1 ms（1.4%）。**量化侧 SIMD 无效。**

#### 1.3 抖动的两点实验：它是「延迟受限」，不是「吞吐受限」

Floyd–Steinberg 的误差扩散是逐像素**非线性**递推：
`carry = (clamp(pixel + rowIn + carry) - palette[lut[...]]) * 7/16`，
clamp 使递推非仿射，无法并行前缀化；R/G/B 三条链本来就并行，
把它们塞进一条 `Vector128` 只是把 3 次标量运算换成 1 次向量运算——**缩短不了链长**。

实验 A —— 去边界检查（指针 + `Unsafe`，逐像素 uop 减少约 40%，md5 一致）：

| | quantize 中位 | 编码 total |
|---|---|---|
| 基线 | 60.22 / 60.47 ms | 78.02 / 78.35 ms |
| 指针版 | 61.70 / 61.58 ms | 79.50 / 79.57 ms |

**零提升，反而慢约 2%。** 每像素少掉约 26 个 uop 却没有收益 ⇒ 热点**不是吞吐受限**，
SIMD 靠「一条指令干多份活」的路子没有可乘之机。

实验 B —— 依赖链探针（把 LUT 与调色板两次依赖加载换成常数，链结构不变）：
quantize **60.8 → 23.3 ms**（抖动 ~54 → ~18.5 ms）。
⇒ ~54 ms 中约 **35 ms 是「贯穿两次依赖 L1/L2 加载」的串行链延迟**，
~18.5 ms 是基础链延迟（≈14 cycle/像素）。抖动基本 100% 由依赖链延迟构成。

### 2. 解码 LZW：可向量化面只有约 1 ms，且下探实测为负

#### 2.1 结构计数（432 万像素）

码数 863,497；**前缀链步数 4,880,199**（5.65 步/码）；补位迭代 1,216,130。
串长分布：≤4 → 763,440 串/171 万像素；5–8 → 66,968/38 万；9–16 → 8,678/9.6 万；
**>16 → 24,186 串/213 万像素（49% 的像素，但只有 2.8% 的串）**。

#### 2.2 消融实测（同一二进制内以探针切换，产物全部逐字节一致）

| 变体 | lzw 中位 | 相对基线 |
|---|---|---|
| 基线（>16 走 SSSE3 pshufb 反序） | 12.76 / 12.92 ms | — |
| 输出**全部**走标量 | 13.80 / 13.84 ms | +0.9 ms |
| **完全跳过输出阶段** | 11.48 / 11.56 ms | −1.3 ms |
| SIMD 反序**下探到 len≥5** | 13.51 / 13.52 ms | **+0.5 ms（变慢）** |

⇒ **整个输出阶段只占 1.3 / 12.8 ≈ 10%**，其中一半已被现有 pshufb 路径拿走；
把 SIMD 下探到 5–16 长度的短串实测**更慢**（每串多一次掩码表加载 + 守卫分支，
抵不过省下的标量拷贝）——与既有结论「快路径不要加罕见边界判断」一致。

⇒ **其余约 90%（11.5 ms）是位流解包 + 字典展开**：

两者在指令级都不可向量化。**解码 LZW 的 SIMD 面 ≤1 ms < 7%，无效。**

### 3. 方法论要点（可复用）

- **同构建内 A/B**：探针用 `static readonly` env 开关切在同一份二进制里，
  避免跨构建/跨会话的 8% 量级漂移。实测同一改动跨进程复测，基线中位数会在
  12.0 ↔ 12.9 ms 之间浮动，因此只做同构建内相对比较。
- **探针代码本身会拖慢基线**：加了 4 个探针分支后，解码 lzw 基线由 12.0 ms 变成 12.9 ms
  （约 +7%）。这既是测量注意事项，也再次验证了上面「快路径不加罕见判断」的教训。
- **先做封死性上界**：像 1.2 那样先算「把所有可动的东西全做成零耗时能拿到多少」，
  比先写 SIMD 再测快得多，也能直接判定一个方向值不值得投入。

### 4. 结论与后续

- 量化侧：**不要做 SIMD**。真要动它，方向是**缩短依赖链**（例如让 LUT/调色板落在 L1、
  或把 35937 字节的 LUT 换成更小的两级表以降低 L2 命中率），而不是向量化。
- 解码 LZW：**不要做 SIMD**。要提速只能改算法（减少链步数/位流解包次数）。
- 之前记录的「下一步要瞄准量化的直方图构建与调色板查找」这条判断可以作废：
  两者合计只占编码 4.3 ms / 5.5%，真正的 73% 在抖动，而抖动受串行链限制。
