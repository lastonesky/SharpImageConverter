这个项目的**内核质量明显高于其外包装**：编解码与 optimize 的实测纪律、SIMD 一致性测试、文档里的否决记录都是稀缺资产。真正的问题几乎都集中在**边界层**——公共 API 的形态、格式注册体系、CLI 的可脚本化程度、以及缺少自动化门禁。

## 1. 数据结构与架构（P0）

### 1.1 两套公开图像模型，能力集互不覆盖 🔶

| | `Image<TPixel>`（Core） | `ImageFrame`（根命名空间） |
|---|---|---|
| 像素格式 | Rgb24 / Rgba32 / **Gray8** | Rgb24 / **Bgr24** / **Bgra32** / Rgba32 |
| 元数据 | `ImageMetadata` | `ImageMetadata` |
| 流式加载 | ✗（只有 `Configuration` 有 Stream） | ✓（含不可 Seek 流 + 严格模式） |
| 处理管线 | ✓ `Mutate/Clone` | ✗ |
| 保存 WebP | ✓ | ✓（2026-10-30 补 `SaveAsWebp` / `.webp` 派发） |
| 保存 alpha | ✓ | ✓（2026-10-30 已修，见下） |

`ImageFrame` 能加载 PNG/WebP 并保留 `Rgba32`，但 `SaveAsPng` 走 `GetRgb24Pixels()`（`ImageFrame.cs:534,638`），alpha 直接消失；`Save` 的 switch 里压根没有 `.webp`（`ImageFrame.cs:479-496`），而 `Load` 支持 WebP。**"读得进、写不出、存丢通道"**。

> **已修（2026-10-30）**：`SaveAsPng` 按 `PixelFormat` 派发（`Rgba32` 直写、`Bgra32` 换序后写、
> 不透明帧自动降为 color type 2 以保持逐字节不变），新增 `SaveAsWebp(path|stream, float quality = 75f)`，
> `Save` 认 `.webp`。回归：`Tests/Codec/ImageFrameSaveTests.cs`（7 例）。
>
> **仍未做**：模型合并本身——两套类型的能力集仍不重叠（`Gray8` 只在 `Image<TPixel>` 侧，
> 流式加载只在 `ImageFrame` 侧，处理管线只在 `Image<TPixel>` 侧）。

建议：确定唯一像素载体。若保留 `ImageFrame`（它更接近真实需求：BGR 面向 Win32/GDI 互操作、支持不可 Seek 流），则把处理管线泛化到它，并把 `Image<TPixel>` 标记 `[Obsolete]` 走一个版本周期；反之亦然。不要长期并存两套。

### 1.2 格式嗅探有三份实现 ✅ 已收敛（2026-10-30）

问题原貌：

| 位置 | 机制 |
|---|---|
| `Configuration.LoadRgb24/LoadRgba32` | 遍历 `IImageFormat.IsMatch`，扩展名只作优先级提示 |
| `ImageFrame.Load` | 硬编码 magic bytes（JPEG/PNG/BMP/GIF/WEBP 五个 if） |
| `ImageOptimizer.DetectFormat` | 自己读 16 字节再判断 |

尺寸读取还另有一份在 `MemoryGuard`（五个 `TryReadXxx`）。加一个 TIFF 要改四处。

**已落地**：新增 `src/Core/ImageHeaderReader.cs` 作为唯一实现——
`Sniff(ReadOnlySpan<byte>) → ImageFormatKind` 与
`TryReadInfo(Stream, ImageFormatKind, out ImageInfo)`（宽高/帧数/渐进标志）。
`ImageFrame.Load`、`ImageOptimizer.DetectFormat`、`MemoryGuard.TryReadDimensions`
全部改为调用它，`MemoryGuard` 里那 250 行私有副本已删除。
`ImageOptimizer.ImageKind` 这个内部枚举也并入 `Core.ImageFormatKind`（公开），
于是 `Image.Identify` 可以直接把它交给调用方。新增格式现在只需改
`ImageHeaderReader` 与注册表各一处。

### 1.3 注册体系与派发逻辑脱节（实测）✅

`Configuration` 提供了 `Register/RegisterFormat/RegisterDecoder/RegisterEncoder(Rgba)` 一整套扩展点，`_formatTypeByExtension` 字典也维护得好好的——但保存时**完全绕过它**：

```csharp
// Configuration.cs:162-169
var ext = Path.GetExtension(path).ToLowerInvariant();
if (ext == ".jpg" || ext == ".jpeg") enc = _encoders[typeof(JpegFormat)];
else if (ext == ".png") enc = _encoders[typeof(PngFormat)];
...
```

实测（`E:\tmp\apiprobe`）：注册一个 `.foo` 格式 + 编码器后 `SaveRgb24(img, "a.foo")` 仍然 `NotSupportedException: 不支持的输出格式`。同理 `RegisterFormat(new FooFormat())` 后加载匹配流会抛 `KeyNotFoundException: The given key 'FooFormat' was not present in the dictionary`（`Configuration.cs:147` 直接索引 `_decoders`）。

修复成本极低且收益明确：保存改为查 `_formatTypeByExtension` → `_encoders`；加载时 `TryGetValue`，缺失时按"该格式不提供 Rgb24 解码"抛 `NotSupportedException` 而不是字典异常。顺带让 `RegisterFormat` 在缺解码器时于注册阶段就报错。

> **已修**（2026-10-30）：见 §0「本批已落地」，回归测试 `Codec/ConfigurationRegistryTests.cs`。
>
> 残留小瑕疵：`Register(...)` 的 `IImageDecoder decoder` 与 `IImageEncoder encoder` 都是必填，
> 无法表达「只有 RGBA 解码器」的格式，只能退化成 `RegisterFormat` + `RegisterDecoderRgba` 两步。
> 后续可把这两个参数改成可空，或提供 `Register(IImageFormat, DecoderSet, EncoderSet)`。

### 1.4 图像缓冲区缺少 stride / owner ⬜

`Image<TPixel>.Buffer`、`ImageFrame.Pixels` 都是 `byte[]`，且**紧打包（无行对齐）**。后果：

- 无法零拷贝接管外部缓冲（GDI `BitmapData.Scan0`、`MemoryMappedFile`、`IMemoryOwner<byte>`）；
- 无法用 `ArrayPool` 复用，143 MP（约 597 MB）峰值时 LOH 压力大——项目自己在 `MemoryGuard` 里花了不少力气绕这个问题；
- 行对齐的编解码器（BMP 有 4 字节对齐，`BmpReader` 内部要单独处理）无法直接对接。

建议：不一定要重写，但至少提供 `ImageFrame.FromMemory(ReadOnlyMemory<byte>, width, height, stride, format)` 的只读入口，让上游把已对齐的缓冲借进来；`Buffer` 保持向后兼容。

### 1.5 动画模型缺失 ⬜

- GIF：`GifAnimation`（`Image<Rgb24>` 列表 + 时长 + 循环数），能读也能写（`GifEncoder.EncodeAnimation(ImageFrame[])`）；
- WebP：`WebpAnimationEncoder`（`Image<Rgb24>` 列表），**只能写不能读**；
- 两者参数类型不同（`ImageFrame` vs `Image<Rgb24>`），没有共同的 `AnimatedImage` 抽象。

GIF→WebP 动画转换目前只存在于 CLI（`ConvertGifToWebp`），库使用者要自己拼。建议引入 `ImageAnimation`（帧列表 + 时长 + 循环 + 每帧处置/混合方式），并让 `ImageFrame` 承载单帧；GIF/WebP 的读写统一到它。

## 2. API 风格与易用性（P0/P1）

### 2.1 门面太窄，且只认路径 🔶

`Core.Image` 静态门面只有 `Load` / `LoadRgba32` / `Save`（实测反射：`Load, Save, LoadRgba32`）。缺失：

- **Stream 入口**：`IImageDecoder` 有 Stream 重载，`ImageFrame.Load(Stream)` 也有，唯独门面没有；`Image.Save(img, stream)` 完全缺失。ASP.NET Core 里"响应流直出"用不了，必须先落盘。
- **`Identify` / `ImageInfo`**：只读宽高/格式/DPI 而不解码。项目内部已有能力（`ImageOptimizer.DetectFormat` + 宽高解析、`PngDecoder.Width/Height`、`BmpReader` 的 out 参数），但没暴露。这对"上传即校验尺寸"的 Web 场景是刚需。
- **Gray8 加载**：`Save(Image<Gray8>)` 存在，`LoadGray8` 不存在（单向）。

建议目标形态（不破坏现有调用）：

```csharp
ImageInfo Identify(Stream);                       // 不解码像素
ImageFrame Load(Stream, LoadOptions? = null);     // 统一入口 + 严格模式 + CancellationToken
void Save(ImageFrame, Stream, SaveOptions);       // 格式显式指定，带 Codec 选项
```

> **已完成（2026-10-30）**：`Image.Identify(string|Stream)`（只读头，不解码像素）、
> `Image.Load(Stream, hint?)`、`Image.LoadRgba32(Stream, hint?)`、`Image.Save(image, Stream, ext)`，
> `Configuration` 侧同名重载；`Core.ImageInfo` 为只读结构
> （`Format`/`FormatName`/`Width`/`Height`/`PixelCount`/`FrameCount`/`IsProgressive`/`IsAnimated`）。
> 回归：`Tests/Codec/IdentifyTests.cs`（13 例）。
>
> **未做**：`LoadOptions`/`SaveOptions` 选项对象（当前只有 `extensionHint` 可选参，`SaveOptions` 类型不存在）、
> `LoadGray8`（`Save(Image<Gray8>)` 仍是单向）。

### 2.2 没有取消能力 ⬜

`CancellationToken` 全库只出现在 JPEG 流式解码链路（`JpegBitReader/JpegDecoder`）。转换、encode、resize、optimize 都没有。CLI 也没有 `Ctrl+C` 处理——143 MP 的 optimize 要跑十几秒到几十秒，用户只能杀进程。

建议：公开 API 统一加可选 `CancellationToken`；CLI 用 `Console.CancelKeyPress` 置位，批处理在文件边界检查并输出"已完成 N/M"。

### 2.3 同步 API 包着异步实现 ⬜

`ImageFrame.LoadJpeg(Stream, bool useStreamingDecoder, ...)`（`ImageFrame.cs:356-389`）内部 `.GetAwaiter().GetResult()`。在有 `SynchronizationContext` 的宿主（WinForms/WPF/老 ASP.NET）里是死锁风险；且三个 `bool` 参数没有名字约束，调用点可读性差。建议提供真正的 `LoadJpegAsync` / `ValueTask` 版本，同步版标注"不保证在 UI 线程安全"。

### 2.4 全局可变静态开关 ⬜

`ImageProcessingContext` 上挂着：

```csharp
public static bool UseQuantizedVnni { get; set; } = true;   // :790
public static int  VnniMinPixelsDownscale { get; set; }     // :805
public static int  VnniMinPixelsUpscale { get; set; }       // :806
public static bool EnableVnniBilinear { get; set; }         // :809
```

进程级可变状态。库使用者（尤其测试并行跑）无法隔离；也不能按下图调优。建议改为 `ResizeOptions` 上的实例属性，静态属性保留为 `[Obsolete]` 的默认值来源。

### 2.5 先建后弃的公开抽象 ⬜

`IImageProcessor`（`Interfaces.cs` 所在文件的同类，`Processing.cs:15`）全仓库 **0 处实现、0 处引用**。公开 API 里留一个没人实现的接口，只会让使用者以为存在插件体系。删除，或真正让 `ImageProcessingContext` 实现它。

### 2.6 三个 resize 方法，没有选项对象 ⬜

`Resize`（最近邻）、`ResizeBilinear`、`ResizeBicubicOptimized`、`ResizeToFit` 并列，语义靠方法名区分，质量/速度取舍无法用参数表达（`bicubic` 的 `a` 系数、是否走 VNNI 都不能传）。建议 `ResizeOptions { Mode, FilterA, MaxWidth, MaxHeight }` 单一入口，旧方法保留转发。

### 2.7 选项类扁平且会篡改入参 🔶

`OptimizeOptions` 28 个属性平铺 4 种格式的策略（`Jpeg*` / `Png*` / `Webp*` / `Gif*`），IDE 里一屏看不完，也无法"只接受 JPEG 相关设置"。建议拆成嵌套：`options.Jpeg.TrellisQuantization`、`options.Webp.MinQuality`。

更实际的问题：`Normalize(OptimizeOptions?)` 的 XML 注释写"返回规范化后的副本"，但实测**原地修改入参并返回同一个引用**：

```
[Normalize] 入参 TargetQuality=100 MaxColors=2；ReferenceEquals=True
```

调用方把同一个 `options` 传给多张图，会拿到被悄悄钳制过的值；若这个实例还是共享的（DI 单例、静态字段），就是跨线程数据竞争。建议改为 `Clone()` + 规范化后返回新实例，或改名 `ClampInPlace`。

> **已完成（2026-10-30）**：新增 `OptimizeOptions.Clone()`，`Normalize` 返回副本，入参不再被改
> （探针 `ReferenceEquals=False`）。剩余：`Jpeg*/Png*/Webp*/Gif*` 的嵌套拆分未做。

### 2.8 CLI 的脚本化能力 🔶

| 问题 | 证据 |

## 3. 行为规范化（P1）

### 3.1 同一类失败，三种表达 🔶

| 场景 | 表现 |
|---|---|
| 跨格式 optimize 时内存超预算 | `throw new InsufficientMemoryException`（`ImageOptimizer.cs:63`） |
| 同格式 optimize 时内存超预算 | 返回 `OptimizationResult.Reason`（:77） |
| 底层分配失败 | `throw new OutOfMemoryException`（`NativeBufferOwner.cs:75`、`SimdHelper.cs:887`、`WebpRowSource.cs:42`） |

三者对调用方是完全不同的契约。建议：**可预期的业务性失败 → `Result`**（`Reason`），**调用方用法错误 → 异常**（`ArgumentException`/`NotSupportedException`），**环境不足 → 单一专用异常**（`InsufficientMemoryException`）。去掉自抛 `OutOfMemoryException`——它是运行时保留类型，`catch (OutOfMemoryException)` 的语义会被污染。

> **已完成（2026-10-30）**：`NativeBufferOwner.cs:75`、`SimdHelper.cs:887`、`WebpRowSource.cs:42`
> 三处自抛改为 `InsufficientMemoryException`。剩余：「可预期失败走 `Result`、用法错误走异常」的
> 总体分工未重排（`ImageOptimizer` 里仍并存两条路径）。

### 3.2 公开编码器不校验像素格式 🔶

`GifEncoder.Encode(ImageFrame, Stream)`（:77）和 `EncodeAnimation`（:230）都直接把 `image.Pixels` 交给按 **3 字节/像素** 索引的 `QuantizePixels`（:98、:254），**不检查 `image.PixelFormat`**。传一个 `Rgba32` 帧进去 → 步长错位，静默产出乱图或越界。`ImageFrame.SaveAsGif` 自己做了守卫（`ImageFrame.cs:609-617`），但公开编码器没有。建议在 `Encode(ImageFrame)` 入口显式 `if (image.PixelFormat != Rgb24) throw` 或内部自动 `ToRgb24()`。

> **已完成（2026-10-30）**：`GifEncoder.Encode(ImageFrame, ...)` 入口校验并抛 `ArgumentException`
> （`Formats/Gif/GifEncoder.cs:88-95`）。
>
> **未做**：`EncodeAnimation`（`:249`）仍逐帧不校验——传 `Rgba32` 帧仍会按 3 字节/像素错位；
> 它也不校验「各帧尺寸与首帧一致」，尺寸不一致时用首帧 `w/h` 编码其余帧。

### 3.3 可变性契约含糊 ⬜

- `ImageFrame.ApplyExifOrientation(int)`：`orientation == 1` 时返回 `this`（不复制），否则返回新实例；并且**顺手把 `Metadata.Orientation` 改成 1**——改的是与原帧共享的元数据对象（`ImageFrame.cs:625-631`）。调用方以为"返回新图、原图不变"，实际原图的 EXIF 已被改写。
- `SwapRgbBgrInPlace()` 修改 `_pixelFormat` 而 `Pixels` 是 `get`-only，文档说"不修改原帧"，但这个类本身是可变的。

建议：统一为"纯函数 + 显式 InPlace 后缀"，并让 `ApplyExifOrientation` 在返回新实例时复制 `ImageMetadata`（`record` 或 `with` 表达式）。

> **未做（现状复核 2026-10-30）**：`ImageFrame.cs:684-690` 仍是原样——`orientation == 1` 返回 `this`，
> 否则先改 `Metadata.Orientation = 1` 再构造新帧（与原帧共享同一个 `ImageMetadata` 实例）。

### 3.4 IDisposable 契约缺口（CA1001/CA1816）✅

- `JpegEncoder.PipeQueue`（:276）持有可释放字段（`SemaphoreSlim` 等）却不实现 `IDisposable`；
- `LzwEncoder.Dispose()` 未调用 `GC.SuppressFinalize`（`LzwEncoder.cs:335`）。

前者在异常路径上有泄漏风险，后者在派生类场景下语义不完整。

> **已修（2026-10-30）**：`PipeQueue` 实现 `IDisposable`（三处流水线在 `Task.WaitAll` 之后显式释放，
> 不用 `using` 以避免与仍在退出的 stage 抢 Wait/Release）；`LzwEncoder.Dispose` 补 `GC.SuppressFinalize`。

### 3.5 `--optimize` 的隐式格式转换 ⬜

项目自己很清楚这个坑（"PNG 内容 + `.jpg` 扩展名 → 隐式转真 JPEG"），但对使用者是反直觉的：`Optimize` 的输入按内容判定、输出按扩展名判定。建议 CLI 加 `--strict-format`（内容与扩展名不符即报错）并在 README 显著位置说明；`OptimizeOptions` 里加 `RequireFormatMatch`。

## 6. 支持的格式（P2）

> 状态：三项均 ⬜，本批未动格式面。

### 6.1 缺失的常用格式 ⬜

| 格式 | 价值 | 成本 |
|---|---|---|
| **TIFF** | 照片/扫描工作流的第二格式，且 optimize 场景常见（未压缩 TIFF 巨大） | 中（LZW/PackBits + 多页） |
| **ICO / CUR** | favicon 生成是"图像转换"最常见的衍生需求 | 低（PNG/BMP 嵌装 + 目录结构） |
| **AVIF** | Web 端现代格式；有 libavif 可直接 P/Invoke，与现成的 libwebp 加载器同构 | 中（新的原生依赖 + 同 RID 打包） |
| **APNG** | 已有 PNG 全套，只差 `acTL/fcTL/fdAT` 三个 chunk | 低 |
| **TGA / QOI / PPM** | 无压缩、极易实现，适合作为"如何接一个新格式"的样板与测试载体 | 极低 |

如果短期不做 TIFF，至少把 `NotSupportedException` 的文案改成可操作的（"当前支持 JPEG/PNG/BMP/GIF/WebP；检测到 TIFF"），而不是笼统的"未知图像格式"。

> **未做（现状复核 2026-10-30）**：`ImageHeaderReader` 已把嗅探收成一处，加「识别后显式拒绝 + 报格式名」
> 的成本已降到很低，但本轮未动——TIFF/ICO 的内容目前仍落到「未知图像格式」。

### 6.2 渐进式 JPEG 只读不写 ⬜

解码支持完整的 progressive（含 successive approximation）；编码侧只有 `JpegProgressiveTranscoder` 这条**后置重编码**路径（spectral selection，无 successive approximation），且只挂在 optimize 上。普通 `--to jpg` 无法产出渐进式。若目标是"给站点省字节"，渐进式的收益（首屏可见）值得一个 `--jpeg-progressive` 直通编码实现。

### 6.3 元数据模型太薄 ⬜

`ExifMetadata` 只有 6 个字段（Make/Model/DateTime×2/GPS），其余靠 `ExifRaw` 原样搬；XMP / IPTC 只作为"可剥离的 APP 段"存在，PNG 的 `eXIf/iTXt/tEXt` 无模型。对"批量压站"场景够用，但一旦要做"按拍摄时间重命名""保留版权信息"，就得自己解析。

建议：把元数据拆成「保留（原样透传）」与「可查询（解析出的字段）」两层，明确写入文档——现在的能力边界只在源码注释里。
