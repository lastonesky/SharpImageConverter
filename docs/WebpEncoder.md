# WebP 有损编码器（VP8）现状与缺口

本文件记录**纯托管 VP8 编码器**（`src/Formats/Webp/Vp8Encoder.cs`）的实现边界、与 libwebp
的实测差距，以及按优先级排列的补齐清单。解码侧与 VP8L 无损侧见 `PerfReport.md` §6.5。

## 1. 已实现

| 环节 | 现状 |
|---|---|
| 帧头 / 量化表 | 1 个 token 分区；`quality → q index` 单调映射；环内滤波强度按 q 分档 |
| 帧内预测 | 16×16：DC / TM / V / H；8×8 色度同四种；**4×4（B_PRED）10 种模式** |
| 模式选择 | **率失真（D + λ·R）**：i4x4 与 16×16 各自完整编码一遍，按重建失真 + 精确码率决胜（见 §3） |
| 变换量化 | 4×4 整数 DCT，Y2 二次变换，标量量化 |
| 熵编码 | 标准 Huffman 表 + 两遍法（第一遍统计 0/1 频次，第二遍自适应概率写位流） |
| 滤波 | 环内滤波对齐解码端顺序，宏块边界（16×16 帧内不启用宏块内部边界） |
| alpha | ALPH 平面 VP8L 无损编码，支持四种预测过滤并自动择优 |
| 两遍决策一致性 | 第一遍 `statsOnly` 只统计、不滤波，且与第二遍共用同一套模式决策 |

## 2. 与 libwebp 的实测差距

1024×1024，同 q，体积比 = 我方 / libwebp（<1 表示我方更小）。

| 内容 | q50 | q75 | q90 | q95 |
|---|---|---|---|---|
| 自然照片 photo | 0.811 | 1.102 | 0.893 | 0.998 |
| UI 截图 ui | 0.845 | 0.987 | 0.959 | 0.959 |
| 合成渐变 grad | 0.664 | 0.927 | 0.941 | 1.079 |
| 文字截图 a_text | 0.913 | 1.182 | 1.025 | 1.044 |
| 纯色面板 rgba_panel | 1.444 | 1.897 | 2.077 | 2.704 |
| 柔渐变 rgba_softgrad | 0.596 | 0.669 | 0.696 | 0.797 |

**同 q 不是等画质**，而且 RD 之后这个偏差变大：q50 时我方 PSNR 比 libwebp 低 0.9~2.4 dB，
体积也只有它的 0.60~0.85——λ 在低质量档更倾向省码率，等于把「同 q」当成了「更省的同 q」。
要等画质比较请看 PSNR 列：q75~q95 双方差距缩到 0.1~0.8 dB，此时体积比在 0.89~1.08
（纯色面板除外）。**纯色面板类仍差 1.4~2.7×**，是当前最大的单点差距，成因是缺分段自适应
量化（§4 第 1 项）。

## 3. 率失真决策（RD）

每个宏块把 i4x4 与 16×16 **都完整编码一遍**（预测 → 变换 → 量化 → 重建），各自得到：

- **D**：重建后的亮度 SSE（不是模式选择用的预测域 SSE——两者不是一回事）；
- **R**：这一路写出去要多少 bit，由「只累加成本、不产出字节」的编码器实例算出。

取 `D + λ·R` 小者。胜者若是 i4x4，就从备份恢复它的重建块与量化数组（16×16 那遍已经把
重建平面覆盖了）。

### 3.1 码率估计复用真实写位函数

给 `Vp8BoolEncoder` 加了成本模式：`BeginCost()` 之后 `PutBit` 只累加
`-log₂P(bit)`（查 `Vp8CostTable`，单位 1/256 bit，全程整数避免跨平台分叉），
不改 range/value。于是 `CostLuma` 可以把 `_part0`/`_tokens` 临时换成这个实例，
**直接复用** `WriteMacroblockModes` / `WriteResidualTokens` / `Vp8ModeTree.Write` ——
码率模型与位流生成是同一段代码，不可能失配。试算结束后回滚 nz 与 i4x4 模式上下文。

精度实测：选中的每一路「估计位数 / 实际写出位数」= **1.00**（grad/photo 差 <0.1%）。

代价是每个宏块多跑两遍写位逻辑（一遍计价、一遍真写），1024² q75 从 110 ms 涨到 128 ms。

### 3.2 踩过的坑：概率语义反了

`Vp8CostTable` 第一版把 VP8 的 `prob` 当成 P(bit=1) 建表，实际它是 **P(bit=0)**
（编码端 bit=0 取 `[0, split)`，split 正比于 prob）。结果常见事件被算成昂贵：
整体成本**高估 4.75 倍**，而且高估倍数随内容漂移（渐变图 4.7×、照片 2.8×）。
后果是 RD 反而比原来的 SSE 门槛差 5%——i4x4 被当成便宜货过度使用。

定位方法：直接对比「估计位数」与「实际写出的位数」（`_part0.Length + _tokens.Length`
的增量），比值 4.75 一眼看出问题不在决策逻辑而在成本模型。

### 3.3 λ 标定

`λQ8 = LambdaScale × y1Ac`：λ 与量化步长成正比（量化越粗，1 bit 能换回的失真越多）。
6 图 × q50/75/90/95 共 24 组，对照旧的「SSE 压到 16×16 的 55% 以内」门槛：

| LambdaScale | 总体积 | 平均 ΔPSNR | 劣于旧门槛的组数 |
|---|---|---|---|
| 150 | −3.04% | +0.010 dB | 0/24 |
| 230 | −3.09% | −0.003 dB | 0/24 |
| **300（采用）** | **−3.11%** | **−0.010 dB** | **0/24** |
| 350 | −3.13% | −0.014 dB | 1/24 |
| 450 | −3.10% | −0.022 dB | 0/24 |
| 600 | −3.15% | −0.026 dB | 0/24 |

曲线在 150~600 之间几乎是平的（体积极差 0.11%）。**这是 RD 相对旧门槛最重要的差别**：
旧门槛的最优值随内容大幅漂移（自然照片偏 40、UI 截图偏 70~100），换一批图就得重标；
RD 的 λ 按量化步长缩放后，整段区间都能用。

`sse16 == 0`（整块完全平坦）时跳过 i4x4 试排——这是精确的提前退出，不是门槛。

## 4. 缺口（按优先级）

1. **分段自适应量化**：`rgba_panel` 的 2× 差距主要来源——libwebp 把平坦区与边缘区分到
   不同 segment，用不同量化步长；配合 segment 的 lf delta 还能按段调滤波强度。
   这是纯色/面板类内容的单点大头。
2. **4×4 模式选择也用 RD**：当前 16 个子块的模式仍按预测域 SSE 选（每个子块 10 个候选，
   全部都做变换量化太贵）。可行做法是 SSE 取前 2~3 名再按 `D + λ·R` 决胜，
   或对系数做 trellis（量化时按 RD 代价选系数值）。
3. **滤波强度参与率失真**：当前按 q 查表定死（`EstimateFilterLevel`）。
4. **无损编码多 pass**：直方图二次优化（用第一遍的实际码长重算 Huffman）、长窗 LZ77。
5. **CLI `--webp-lossless` 与 `SaveOptions.WebpLossless`**：编码器支持无损，但入口未暴露。
6. **动图解码改按帧流式**：当前每帧 `canvas.ToArray()`，内存 O(帧数 × 画布)。
7. **静态 VP8X canvas 尺寸与帧尺寸交叉校验**。

## 5. 踩过的坑

- **B_PRED 模式树写错一位就整体错位**：解码端 `kBModesProba` 的树里 B_HE 需要
  `p0..p2=1, p3=0, p4=0` 共 5 位，写侧曾漏掉最后一位。表现是 64×64 q75 的 PSNR 从
  40.7 掉到 12.0 dB，而两支解码器（我方 + libwebp）互相一致——位流合语法，只是模式读错。
  定位方法是给布尔编/解码器加位级 trace（记录 `(bit, prob, 语法段)`），第 1364 位处
  编码端用 `p[0][3][0]=56`、解码端用 `p[1][9][4]=197`，由此反推出「解码端多读了一位」。
  现已把模式树抽成 `Vp8ModeTree` 单一实现，并加全组合往返测试。

- **单值 setter 手写构造参数会静默丢字段**：`WebpEncoderOptions` 有四项目，而
  `WebpEncoderAdapter(.Rgba)` 的 Quality / Method / ConcurrencyStrategy 三个 setter
  各自写 `new WebpEncoderOptions(...)`，末尾的 `lossless` 有默认值 `false`，编译期
  毫无提示。后果是 `adapter.Lossless = true` 之后只要再设一次 `Quality`，产物就从
  VP8L 静默退回 VP8 有损——字节数变了，但没有任何异常或警告。现在 setter 统一用
  `Options with { ... }`（`WebpEncoderOptions` 为此改成 `readonly record struct`），
  `WebpEncoderOptionsTests` 对 6 条 setter 逐个固定「其余字段不变」。

- **文档漂移是真实的回归源**：`WebpDecoder` 类头一度写着「仅剩 ALPH level-reduction
  与 VP8 非关键帧两类不支持」，而 ALPH 的 `preprocessing` 0/1 早已支持、四种预测滤波
  后来也补齐了。`WebpContainerKind.Vp8` 的注释同样停在「本批不支持解码」。这类注释
  会误导调用方把正常输入当损坏数据，现在改为按 `WebpUnsupportedException` 的实际抛出点
  列举，并注明「修改时请核对抛出点，不要凭印象写」。
- **i4x4 的重建与模式选择必须逐块交错**：子块 n 的预测要读已重建的 n−1 / n−4，
  不能先算完 16 个子块的 SSE 再统一变换（那不成立）。因此「先判定再选路」不可能省掉
  被否决宏块的重复工作。
- **`top_right` 的三个写入位置是第 3/7/11 行右侧**（对应 C 里 `top_right` 指针按 BPS
  步进），不是第 0/4/8 行；最右列宏块要把上一行右侧 padding 归一化为边缘像素，
  否则下次读到陈旧值。
